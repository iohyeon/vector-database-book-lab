# 서평에 넣을 실습 후기 초안

> 아래 글은 『벡터 데이터베이스』 서평의 ‘직접 해 본 실습’ 부분에 넣기 위해 작성한 초안이다. 이 저장소에서 실행한 범위만 경험으로 서술했다.

## 책의 설명을 실제 검색 결과로 확인해 보기

책을 읽으면서 가장 궁금했던 것은 “의미가 비슷한 문서를 찾는다”는 설명이 실제 쿼리에서는 어떻게 보일까 하는 점이었다. 그래서 책의 3~5장에 연결되는 실습을 세 가지로 나누어 CLI에서 실행했다. FAISS로 인덱스의 속도와 재현율을 비교하고, SQLite로 원본과 인덱스의 ID 연결을 확인한 뒤, PostgreSQL과 pgvector에 실제 문장 임베딩을 저장해 검색했다.

공개할 수 있는 실습 자료가 필요해 고객 지원 문서 12개를 직접 작성했다. 각 문서를 두 문단으로 나누어 24개 청크를 만들고, 책에도 등장하는 `all-MiniLM-L6-v2` 모델로 384차원 임베딩을 생성했다. 모델은 FastEmbed의 ONNX 실행기로 돌렸으며, 벡터와 제목·카테고리·본문은 PostgreSQL에 저장했다. 질문이 들어오면 같은 모델로 질문을 임베딩하고 `pgvector`의 코사인 거리 연산자로 관련 청크를 찾는다.

첫 질문은 **“I want my money back.”**이었다. 문서에는 이 표현 대신 `refund`라는 단어가 들어 있다. 내가 사용한 PostgreSQL의 기본 키워드 비교(`plainto_tsquery`)는 이 질문에 해당하는 결과를 한 건도 찾지 못했다. 벡터 검색은 `Check refund status`, `Refund policy`, `Damaged item on arrival`의 관련 문단을 상위에 올렸다. 두 번째 질문인 **“Where can I get a receipt for my order?”**에서는 카테고리를 `billing`으로 제한했다. 검색 결과 상위 두 개는 모두 `Download an invoice` 문서의 청크였다. `receipt`와 `invoice`처럼 표현이 달라도 같은 맥락의 내용을 찾는다는 1장의 설명을 눈으로 확인한 순간이었다.

![pgvector 의미 검색 실행 결과](../results/pgvector_terminal.png)

하지만 여기서 “벡터 검색이 키워드 검색보다 항상 낫다”라고 결론 내릴 수는 없다. 이번 키워드 비교는 입력 단어를 모두 요구하는 단순한 방식이고, 문서 수도 12개뿐이다. 실제 서비스라면 동의어 사전이나 더 나은 키워드 검색, 그리고 두 방식을 결합한 하이브리드 검색을 함께 검토해야 한다. 또 출력된 코사인 점수 0.388이나 0.557은 정답일 확률이 아니다. 모델과 문서가 달라지면 점수의 분포도 달라지므로, 고정된 임곗값부터 정하기보다 실제 질문과 정답 문서로 검색 결과를 평가하는 편이 맞다.

이 실습에서 새로 보인 문제도 있다. 두 번째 질문에서는 **같은 고객 지원 문서의 두 청크**가 결과 1위와 2위를 차지했다. 검색 엔진에는 서로 다른 청크지만 사용자에게는 같은 문서가 두 번 보이는 셈이다. 5장의 논문 검색에서 “청크로 찾고 논문으로 보여 준다”는 설계가 왜 필요한지 이해됐다. 검색 결과를 사용자에게 보여 주려면 청크를 문서 ID로 묶고, 어떤 청크를 대표 결과로 삼을지 정해야 한다.

FAISS 실습에서는 64차원 난수 벡터 1만 개를 놓고 정확 검색인 Flat과 IVF·HNSW를 비교했다. IVF의 `nprobe`를 1에서 100으로 늘리자 상위 5개 기준 재현율은 0.078에서 1.000으로 올랐고, 질의 시간도 0.0242ms에서 0.4387ms로 늘었다. HNSW도 탐색 폭을 키우자 재현율이 올랐다. 흥미로웠던 것은 이 작은 데이터셋에서 높은 재현율로 설정한 HNSW가 Flat보다 빠르지 않았다는 점이다. 3장에서 배운 “빠른 근사 검색”을 무조건 적용하는 대신 데이터 규모와 원하는 재현율을 먼저 측정해야겠다고 생각했다. 이 수치는 난수 벡터를 쓴 한 번의 환경에서 나온 값이라 실제 문장 검색 성능으로 일반화할 수 없다.

![FAISS 검색 재현율과 지연 시간 실행 결과](../results/faiss_terminal.png)

SQLite 예제로는 4장의 `rowid` 함정을 벡터 확장 없이 최소 재현했다. 원본 행과 인덱스 쪽 ID가 모두 1인 상태에서 `INSERT OR REPLACE`로 원본을 갱신하자 원본 ID만 2로 바뀌었다. 반면 UPSERT에서는 ID가 유지됐다. 검색 결과가 아무리 관련성이 높아도 원본 데이터와의 연결이 끊기면 쓸 수 없다는 점에서, 이 부분이 가장 백엔드답게 다가왔다. 실제 `sqlite-vss` 검색을 돌린 결과는 아니므로 글에도 **ID 연결 동작만 확인한 실습**이라고 명시하려 한다.

![SQLite 원본·인덱스 ID 연결 실행 결과](../results/sqlite_terminal.png)

이번에 실행한 시스템은 **의미 검색까지**다. Ollama나 다른 LLM으로 답을 생성하는 RAG는 붙이지 않았다. 그래도 문서를 자르고, 같은 모델로 저장·질문 벡터를 만들고, pgvector에서 메타데이터 조건과 함께 검색해 원문 청크를 돌려주는 경로는 직접 확인했다. 이 경로가 제대로 작동해야 그 위에 생성 단계를 올렸을 때도 답의 근거를 추적할 수 있겠다고 느꼈다.
